# 브동산 — 전체 인수인계서 (마스터 기준 문서)

이 문서는 브동산 프로젝트의 8개 문서에 흩어져 있는 **모든 기준/규칙**을 한 곳에 모은 인수인계서다. 새로운 방(세션)이 이 프로젝트를 이어받거나, 다른 팀(전략기획/IT/디자인/포스팅 작업방)이 협업할 때 이 문서 하나만 읽어도 "브동산이 무엇을 어떤 기준으로 만들고 있는지" 파악할 수 있게 하는 것이 목적이다. 각 항목의 더 상세한 배경·변천사는 괄호로 표시한 원본 문서를 참고.

**작성일: 2026.09.12**

---

## 1. 프로젝트 개요

- **이름**: 브동산 = "브랜드" + "부동산". 브랜드와 부동산에 관한 인사이트를 공유하는 공간.
- **사업**: 부동산 정보(청약·분양) 제공 홈페이지 운영 + 브랜드 인사이트 콘텐츠. 목표는 콘텐츠를 통한 수익화(광고·제휴)와 자동화된 포스팅 파이프라인.
- **운영**: Paul(사업 운영·의사결정·리서치 자료 제공) + Claude(리서치·작성·디자인·IT 실행) 2인 체제.
- **홈페이지**: `brandongsan.com` (canonical `[www.brandongsan.com](https://www.brandongsan.com)`), GitHub 저장소 `zzanghyuny/brond` + Vercel 자동배포로 실제 배포 완료.
- **운영 방(room) 구조**: 포스팅 제작(리서치·작성·이미지삽입·적정가분석·퍼블리시)은 하나의 방에서 전담 진행. 전략기획팀/IT팀/디자인팀 등 여러 방이 있을 수 있으나 실제 산출물은 이 프로젝트 문서(Projects)를 통해 공유된다. (`company-plan.md`)

## 2. 디자인 기준 (전 콘텐츠·전 페이지 공통, `design-guideline.md`)

### 2-1. 디자인 철학
- **애플처럼 심플하고 색을 많이 쓰지 않는 세련된 디자인.** 모든 디자인 결정의 기본 기준.
- 로고처럼 되돌리기 어려운 결정은 여러 방향을 나란히 비교한 뒤 확정한다.

### 2-2. 컬러 팔레트 (화이트/블랙 모노톤, 최종 확정)
- 배경 흰색(`#FFFFFF`), 텍스트 검정(`#111111`), 보조 회색(`#555555`/`#8A8A8A`), 구분선 연회색(`#E3E3E3`).
- **컬러는 이미지 자료(사진)에만 허용된다.** 그 외 UI 요소(로고, 차트, 버튼, 배지 등)는 예외 없이 흑백만 사용. (2026.09.12부로 레이더 차트 범례 색상도 컬러 → 흑백 농도 구분으로 재정리 완료.)

### 2-3. 타이포그래피
- 나눔고딕(Nanum Gothic). 나눔바른고딕 요청이 있었으나 구글 폰트에 없어 대체.

### 2-4. BI(로고) — 최종 확정, 절대 재검토하지 않음
- **순수 워드마크, 장식 없음.** "브"(브랜드) = 나눔고딕 굵게(800, 검정 `#111111`), "동산"(부동산) = 가볍게(400, 회색 `#555555`). 무게 차이로 브랜드+부동산의 결합을 표현.
- **밑줄·포인트 컬러·원형 뱃지 등 어떤 장식도 없다.** (밑줄 딥 네이비 버전, 원형 뱃지 버전 모두 검토 후 최종 기각됨 — 재검토 금지.)
- 사이트 셸(index/about/contact/privacy/realestate/brand.html)과 포스팅 파일(1호·2호·브랜드 언박싱 No.001) 전부 이 최종본으로 통일 완료(2026.09.12).
- 로고 캔버스(Design Artifact): https://claude.ai/code/artifact/a7d9d1b4-4ea3-4f4a-b4d2-baa36c6612c2

### 2-5. 포스팅 레이아웃 컨벤션
상단 브레드크럼("— 브동산") → 제목 → 아바타+작성자+날짜+시리즈번호 → 구분선 → 커버 이미지(실사) → 본문 → 하단 AD 상담카드(흑백, "AD·광고" 배지 명시) → 푸터. 사진은 `.photo-block`(테두리 1px 연회색 + 작은 회색 출처 캡션)으로 통일. **콘텐츠 도메인(부동산이든 브랜드든) 무관하게 모든 포스팅에 이 스타일 적용.**

### 2-6. 홈페이지 대문(히어로)
- 이미지(라인아트 일러스트 등) 없이 **텍스트 중심**으로 확정(2026.09.08). 관련 시안은 폐기.

## 3. 콘텐츠 제작 기준 — 공통 (콘텐츠 도메인 무관, `process-brand.md`)

### 3-1. 톤앤매너
- **"담백하고 과장 없는" 논조.** 좋은 정보만 나열하지 않고 리스크·미달·공급집중 등 불리한 사실도 균형 있게 제공한다.
- 말단 광고(판매원 연락처) 섹션은 반드시 "AD·광고"로 명확히 표기, 이름은 "(가상 예시)"임을 명시(실제 인물 사칭 방지).
- **본문 중간에 "투자 조언이 아니다"류 면책 문구를 넣지 않는다.** 이런 문구는 포스팅 맨 아래 `<footer>`에 한 번만 들어간다 — 핵심요약이나 결론에 중복해서 넣지 않는다(2026.09.08 결정, 기존 포스팅도 전부 정리 완료).

### 3-2. 이미지 삽입 기술 절차 (반드시 이 절차로 재사용)
- Artifact는 외부 이미지 호스트를 CSP로 차단 → **data: URI(base64) 인라인 임베드 필수.**
- base64 텍스트를 대화 컨텍스트나 Edit/Write 툴 파라미터에 직접 붙여넣지 않는다(토큰 폭발 방지). 항상: ① bash+PIL로 리사이즈(900~1400px)·압축(사진은 JPEG 82~85, 단순색 이미지는 PNG quantize) → ② 별도 python 스크립트로 base64 인코딩 후 앵커 문자열 치환 → ③ tag-balance 검증 후 같은 Artifact URL로 재퍼블리시.
- **모든 `<img>` 태그에 `style="width:100%;display:block;"`을 반드시 직접 박아넣을 것 — 전역 CSS에 기대지 말 것 (2026.09.12 확정, 중요).** Artifact 미리보기 스켈레톤에는 `img{max-width:100%}` 전역 규칙이 있어 인라인 width가 없어도 우연히 정상으로 보이지만, IT팀이 실사이트용으로 wrapper를 벗겨내면 이 규칙도 함께 사라져 인라인 width 없는 이미지만 원본 픽셀 크기로 삐져나온다. 실제로 상동역 2호 포스팅에서 지도 이미지 1개만 이 스타일이 빠져 실사이트에서만 폭이 깨지는 버그가 발생한 적 있다 — 새 이미지를 넣을 때마다 스크립트 자체에서 이 스타일이 실제로 붙는지 확인할 것.

### 3-3. 말단 AD 카드 — "광고 신청하기" CTA (모든 포스팅 표준 구성요소)
- `.sponsor` 카드(가짜 소비자용 상담 예시)와 별개로, **실제 광고주(부동산·분양팀장)가 광고를 신청할 수 있는 진짜 동작하는 CTA**를 점선 구분선 아래에 추가.
- 구성: 안내 문구 + "광고 신청하기" 버튼(`.btn-outline`, mailto 링크로 단지명 자동 기입된 제목/본문) + 이메일 주소(`<code>`) + "복사" 버튼(클립보드 API + execCommand 폴백).
- 새 포스팅 작성 시 **처음부터 포함시킬 것** — 나중에 추가하는 게 아니라 AD 섹션의 기본 구성 요소.

### 3-4. 이미지 저작권 정책 (브랜드 콘텐츠처럼 제3자 이미지가 필요한 경우)
- 원 브랜드/제작사 저작권이 있는 이미지·영상은 **직접 다운로드해 게시하지 않는다.**
- 대신 브동산 자체 제작 추상 SVG 커버 + 원본으로 연결되는 출처 링크로 대체. 사용 조건이 확실한 이미지(공식 press kit 등)를 Paul이 직접 확보해 주는 경우가 아니면 이 정책이 기본.

### 3-5. 외부 리소스 제약 (인프라 레벨, 세션 승인으로 해제 불가)
- Claude는 클라우드 세션에서 임의 웹사이트의 이미지를 직접 다운로드/캡처할 수 없다. → Paul이 채팅에 직접 첨부하는 방식으로만 이미지 확보.
- 부동산 시세·공급물량 데이터: 호갱노노·직방·아실·부동산R114는 WebFetch 대부분 차단. **KB부동산(kbland.kr)만 안정적으로 조회 가능.**

## 4. 콘텐츠 제작 기준 — 부동산 전용 (`process-realestate.md`)

### 4-1. 단지 선정
- 다룰 청약 단지는 **Paul이 매일 직접 선택**한다. Claude가 임의로 고르지 않는다.

### 4-2. 포스팅 고정 양식
1. 핵심 요약 ("이 단지, 적정가는 얼마일까?" 훅 + 예상 프리미엄 수치)
2. 입지 분석
3. 상품 분석
4. 공급이 많을까, 적을까 (Supply Check)
5. 결론
- 체크리스트(계약/매수 전 확인사항) 섹션은 넣지 않는다.

### 4-3. 적정가 산출법 — "브동산 모형" (GS건설 GS RIS 모형 기반, 매 포스팅 Claude가 스스로 산출)
**절차**: 비교단지 2곳 선정 → 같은 크기 타입 KB시세(총액) 확인 → 평점 채점 → 평점·연령 보정 → 적정가 산출.

1. **비교단지 선정**: 기본은 Claude가 SITE와 평점이 비슷한 2곳 자체 선정(지역 랜드마크·실거래 활발한 곳 우선). **Paul이 지도와 함께 직접 지정하면 그걸 그대로 사용.** 지도에서 비교단지를 못 찾았다고 곧바로 "지도 범위 밖"으로 단정하지 말 것 — 지도 전체를 한 번 더 훑어보거나 Paul에게 위치를 재확인한다(2026.09.12, 검암역로열파크씨티 푸르지오 사례: 실제로는 지도 프레임 안에 있었는데 처음에 놓쳤던 것으로 드러남).
2. **기준가격**: KB시세를 1차로 시도하되, **같은 크기 타입끼리 총액으로만 비교** — 평당가/㎡당가 환산은 계산·결과 어디에도 절대 노출하지 않는다. 타입 매칭 우선순위: 1순위 전용 84㎡(83~85㎡ 동일 취급, 전용률 차이로 실질 110~125㎡도 84 동일면적 취급, 공급면적 표기 단지는 "공급 109㎡=전용 84㎡=34평"으로 환산), 2순위 전용 59㎡.
   - **KB부동산(kbland.kr)은 JS 렌더링 SPA라 WebFetch 요약이 실제 페이지에 없는 가격을 지어내는(hallucination) 경우가 확인됐다(2026.09.12).** 타입별 시세는 곧바로 신뢰하지 말고 원문 문장을 그대로 인용해 재확인을 요청할 것. 못 믿을 값은 버리고 **리치고(richgo.ai) 평형별 시세**를 1차 폴백으로 사용한다.
3. **평점표(100점 만점, 3항목)**:
   - 입지성(40) = 교통환경(20)+주거편의(10)+교육환경(10)
   - 브랜드(20) = 대기업 상위브랜드(자이·래미안·힐스테이트·푸르지오·이편한세상·더샵·롯데캐슬·아이파크·SKVIEW)=20 / 대기업 중위·대형=16 / 중견=12 / 중소=8 / 비브랜드=0
   - 단지특성(40, 표기는 "상품성") = 상품수준(10)+세대수(10)+조망권(10)+주차장(5)+건폐율(5)
   - 지역수요공급·가산점·감점 항목은 전부 폐지됨(데이터 접근 한계).
4. **보정 및 적정가 계산**:
   - 평점보정 배율 = 1 ± (SITE-비교단지 점수차 × 0.01), 최대 ±20%.
   - 연령보정 배율(**"OO%"=곱하는 배율**, 예: "120%"=1.2를 곱한다는 뜻):
     - 0~10년: `1 + (연식차이개월수/120) × 0.2`
     - 10~20년: `1.2 + ((연식차이개월수-120)/120) × 0.3`
     - 20년 초과: 1.5 고정
   - **연식 차이 기준 시점 = SITE의 준공예정년월** (현재 시점이 아님 — SITE는 미래에 완공되므로).
   - 보정가격(총액) = KB시세(동일크기 타입 총액) × 평점보정 × 연령보정.
   - **적정가격(총액) = 2개 비교단지 보정가격의 평균.** 두 값 차이가 10% 넘어도 재선정 없이 그대로 평균 사용.
5. **핵심요약 시각화**: 입지/브랜드/상품성/연식 4축 레이더 차트(SITE vs 비교단지 2곳, **전부 흑백 톤** — 굵기/실선·파선·점선으로 구분) + 항목별 평점 비교표(입지/브랜드/상품성/종합평점/연식가산율/84㎡ 기준가/보정가격, 헤더에 건설사·세대수·입주시기 병기, 연식 가산율 행에 "10년1개월차·×1.2025"처럼 연차 병기) + 항목별 한줄평. **평당가·㎡당가는 표에도 절대 노출하지 않는다.**

### 4-4. 지도 어노테이션 절차
- Paul이 마커 찍은 지도를 주면 PIL+numpy로 색 채널 탐지 → 통일된 색 체계로 재작도. **SITE=빨간 박스/핀, 비교단지 1·2=초록(동일색, 라벨 박스 크기도 동일), 배정초등학교=파란 박스/핀.** 한글은 Noto Sans CJK KR 폰트.
- 지도 자체에 이미 빨강 등 색 요소(경계선·점선 등)가 많으면 순수 색상 임계값 탐지는 오탐이 많다 — 이럴 땐 자동 탐지를 고집하지 말고 지도를 여러 구역으로 크롭해 `Read`로 직접 눈으로 확인하며 좌표를 특정하는 방식이 더 빠르고 정확하다.
- **비교단지가 안 보인다고 곧바로 핀을 생략하지 말 것(2026.09.12)**: 실제로 지도 프레임 안에 있는데 처음 확인에서 놓친 사례가 있었다. 핀을 생략하기 전에 지도 전체를 다시 훑어보거나 Paul에게 위치를 확인한 뒤 결정하고, 그래도 진짜 범위 밖일 때만 "핀 생략 + 캡션에 텍스트로만 표기" 규칙을 적용한다.

3. **가격처럼 계산에 직접 들어가는 숫자는 자동조회 결과를 곧바로 믿지 말 것.** KB시세(kbland.kr)가 실제 페이지에 없는 값을 지어낸(hallucination) 사례가 확인됐다 — 원문 verbatim 재확인 후 사용, 못 믿을 땐 리치고(richgo.ai)로 대체.
4. **지도에서 뭔가를 못 찾았다고 곧바로 결론 내리지 말 것.** 비교단지가 지도 범위 밖이라고 단정하기 전에 지도 전체를 한 번 더 훑어보거나 Paul에게 재확인한다 — 실제로 프레임 안에 있었는데 처음에 놓친 사례가 있었다.
5. **이미지에는 항상 인라인 `style="width:100%;display:block;"`을 직접 넣을 것.** Artifact 미리보기와 실사이트의 CSS 환경이 달라서, 전역 CSS에 기댄 이미지는 미리보기에서는 멀쩡해 보여도 실사이트에서만 깨질 수 있다.
6. **HTML 마크업과 CSS 정의는 항상 짝으로 검증할 것.** 새 컴포넌트(레이더 차트 등)를 추가할 때 마크업만 넣고 `<style>` 블록에 클래스 정의를 빠뜨리는 실수가 있었다 — 게시 전 관련 클래스명을 grep해서 정의가 실제로 존재하는지 확인.
7. **표기 기준(공급면적 vs 전용면적) 차이를 "데이터 없음"으로 오판하지 말 것.** 타입이 안 보이는 게 아니라 표기 기준이 다른 경우가 있다(예: 공급 109㎡=전용 84㎡=34평).
8. **임의 판단으로 비교단지를 바꾸거나 데이터를 생략하지 말 것.** Paul이 지정한 값이 지리적으로 애매하거나 타입 표기가 안 맞아 보여도, 먼저 Paul에게 확인 후 처리한다.
